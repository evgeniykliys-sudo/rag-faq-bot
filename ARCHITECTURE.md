# Архитектура: rag-faq-bot

## Цель (1 предложение)
Telegram-бот, отвечающий на вопросы по внутренней базе знаний (FAQ по AI-платформе) — не выдумывает ответ, а ищет релевантные фрагменты документов и передаёт их модели как контекст, с указанием источника.

## Модули
| Модуль | Файл | Описание |
|--------|------|----------|
| Индексация базы знаний | ingest.py | Читает markdown-документы из documents/, режет на чанки, считает эмбеддинги (sentence-transformers), сохраняет в ChromaDB |
| RAG-поиск и ответ | rag.py | Эмбеддинг вопроса → топ-k релевантных чанков из ChromaDB → промпт с контекстом → Claude API → ответ с указанием источника |
| Точка входа, бот | bot.py | Принимает вопрос текстом, вызывает rag.py, отправляет ответ |

## Стек
- Python 3.12
- sentence-transformers (эмбеддинги, модель `all-MiniLM-L6-v2` — работает локально, без внешнего API)
- ChromaDB (векторное хранилище, persistent client)
- anthropic SDK (генерация ответа на основе найденного контекста)
- aiogram 3.x

## Схема
```
documents/*.md → ingest.py (chunking + embeddings) → ChromaDB (persistent, chroma_db/)

Telegram-вопрос → bot.py → rag.py:
  1. embed(вопрос)
  2. ChromaDB.query(top_k=3) → релевантные чанки + источник
  3. Claude API: system-промпт "отвечай только на основе контекста" + чанки + вопрос
  4. Ответ + "Источник: <файл>"
```

## Почему так, а не просто спросить модель напрямую
Без RAG модель либо не знает внутренних деталей (лимиты, коды ошибок конкретной платформы), либо галлюцинирует правдоподобный, но неверный ответ. RAG заземляет ответ на реальных документах и даёт возможность проверить источник.

## Ограничения демо-версии
- База знаний — 6 синтетических документов для демонстрации техники, не реальная корпоративная документация
- Эмбеддинги считаются локально (CPU), для больших баз знаний в проде обычно используют managed-сервис эмбеддингов
- Чанкинг — по параграфам, без учёта семантических границ (в проде — recursive/semantic chunking)
